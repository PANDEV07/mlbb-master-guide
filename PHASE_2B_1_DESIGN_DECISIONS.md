# PHASE 2B.1 – Design Decisions Register

| Decision ID | Problem | Options Considered | Selected Approach | Rationale | Trade‑offs | Database Enforcement | Status |
|-------------|---------|-------------------|-------------------|-----------|------------|----------------------|--------|
| DD‑001 | How to reference heterogeneous domain entities (Hero, Item, Emblem, BattleSpell) from claims and other tables? | 1. Polymorphic FK (`entity_type` + `entity_id`) without a common table. 2. Separate FK columns per domain. 3. Central **KnowledgeEntity** registry. | **Central KnowledgeEntity registry** (single table with `entity_id`, `entity_type`). | Provides a single target for all foreign keys, avoids conditional FK limitations of PostgreSQL, and keeps a stable UUID per entity. | Requires an extra join to domain‑specific tables for detailed attributes. | `domain tables` FK to `KnowledgeEntity.entity_id` (ON DELETE RESTRICT). Claims reference `KnowledgeEntity`. | PROPOSED |
| DD‑002 | Prevent overlapping active profiles for the same entity & server version. | 1. UNIQUE composite (`entity_id`, `server_version`, `effective_from`, `effective_to`). 2. Exclusion constraint on range. 3. Application‑level trigger. | **PostgreSQL EXCLUDE constraint** using `tstzrange` with GiST. | Guarantees non‑overlap at the DB level, efficient query planning, no need for custom triggers. | Requires GiST index support; slightly more complex DDL. | `EXCLUDE USING gist (entity_id WITH =, server_version WITH =, effective_range WITH &&)` per profile table. | PROPOSED |
| DD‑003 | Model provenance linking sources, evidence, claims, and stance. | 1. Simple claim table with `source_url` text. 2. Full provenance schema (Source → Evidence → Claim → ClaimEvidence). | **Full provenance schema** as defined in `PHASE_2B_1_PROVENANCE_MODEL.md`. | Allows traceability, multiple evidence per claim, stance semantics, and independent verification workflow. | More tables increase schema size; requires careful maintenance. | FK constraints as specified; `ON DELETE RESTRICT` to avoid orphan records. | PROPOSED |
| DD‑004 | Represent item component relationships without cycles. | 1. Self‑referencing many‑to‑many with a check constraint. 2. DAG enforcement at application layer. | **Self‑referencing many‑to‑many `ItemComponent`** with `quantity` and `order_index`; cycle prevention documented as application‑level responsibility. | Simpler DB schema; PostgreSQL cannot enforce DAG natively. | Relies on application logic to detect cycles; potential for accidental cycles if not validated. | FK from `ItemComponent.parent_item_id` and `component_item_id` to `Item.item_id`. No DB‑level cycle check. | PROPOSED |
| DD‑005 | Build model versioning and context representation. | 1. Single `Build` with unique constraint on context fields. 2. Separate `BuildVersion` table linked to `BuildContext`. | **Separate `BuildVersion` linked to `BuildContext`**; multiple versions can share the same context. | Supports multiple reasoning paths for the same situation, keeps history of build changes. | Slightly more joins when retrieving the latest version. | FK `BuildVersion.build_id → Build.build_id`; `BuildContext` FK to `HeroProfile`. Unique constraint on (`hero_profile_id`, `role`, `lane`, `game_phase`, `ranked_mode`). | PROPOSED |

*All decisions are currently **PROPOSED** pending user approval.*
